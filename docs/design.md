# Packet Atlas 設計書 — ネットワークプロトコル解説サイト

Nov 5, 2026 · @naga

## 概要

インターネットのプロトコルを「パケットが飛ぶシーケンス図」と「バイト単位の分解」で学べる静的サイトを、ゼロから自作する。基礎プロトコル17本に、リアルタイム通信の4本(WebSocket・WebRTC・ゲームのネットコード・WebTransport)を加えた全21レッスン、6部構成とする。サイト名「Packet Atlas」は仮称。

### オリジナリティの方針

参考にした既存サイトは、着想(パケットのアニメーション+バイト分解)の出発点としてのみ扱う。次のものは一切持ち込まない。

- ソースコード、CSS、画像、OGP画像、アイコン、フォント構成
- 説明文、レッスンの構成順や見出し、例として使われている具体的なバイト列・ホスト名
- 配色・レイアウト・ネットワーク図の描き方(ノート PC とルーターの絵など)

説明文とバイト列はすべてRFC等の一次資料から書き起こす。参考サイトのHTMLを取得・解析する作業もしない。

### 出発点

この会話で作ったプロトタイプ「リアルタイム通信を、1パケットずつ」(単一HTML、`realtime-protocols.html`)は自作物なので、デザインとデータの土台としてそのまま流用してよい。リアルタイム4章の本文とバイト列はこれを移植する。

### 対象読者

Web・インフラのエンジニア、情報系の学生。日本語を先に作り、英語を後から足せる構造にする。

## 技術スタックとリポジトリ構成

Next.js(App Router)を `output: 'export'` で完全な静的サイトとして書き出し、Vercelに置く。サーバー処理は持たない。レッスンの中身はTypeScriptのデータファイルで書き、型とテストで正確性を守る。

| 項目           | 採用                                                                    | 理由                                                                 |
| -------------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------- |
| フレームワーク | Next.js 15+ / App Router / 静的書き出し                                 | 慣れたスタック。全ページをビルド時に生成できる                       |
| 言語           | TypeScript(strict)                                                      | レッスンデータの型チェック                                           |
| スタイル       | CSS Modules + CSS変数                                                   | テーマ切り替えをCSS変数だけで行う。UIライブラリは使わない            |
| 図             | 自作のReact SVGコンポーネント                                           | 外部の図ライブラリは使わない。アニメーションは requestAnimationFrame |
| フォント       | next/font で IBM Plex Sans JP / IBM Plex Mono を自己ホスト              | どちらもOFLライセンス                                                |
| テスト         | Vitest(データとバイト列)、Playwright + axe-core(画面とアクセシビリティ) | 正確性と操作性を自動で確認                                           |
| 多言語         | `/[locale]/...` のルート、UI文言は辞書、本文はロケール別ファイル        | 日本語先行、英語は後から                                             |
| ホスティング   | Vercel(Cloudflare Pagesでも可)                                          | 静的ファイルなのでどこでも動く                                       |

## データモデル

レッスンは「レーン(登場する機器)」と「手順」の並びで、手順は「矢印(ホップ)」と「パケット」を持つ。プロトタイプの配列形式を、名前付きの型に置き換えたものが下の定義になる。

```ts
// src/lessons/types.ts
export type HopKind = 'control' | 'signal' | 'media' | 'data';

export interface Lane {
  id: string;          // 'client', 'server', 'stun' など。レッスン内で一意
  name: string;        // 表示名
  sub?: string;        // 補足(例: 'ws://example.com/chat')
}

export interface Hop {
  from: string;        // Lane.id
  to: string;          // Lane.id。from と同じなら「手元の処理」として箱で描く
  label: string;       // 矢印の上の短い文字(全角12文字程度まで)
  kind: HopKind;
  lost?: boolean;      // 途中で消えるパケット
}

export interface BitField {
  name: string;
  bits: number;        // 幅(合計がそのバイト数×8になること)
  desc?: string;
}

export interface Field {
  name: string;
  hex?: string;        // '81 85' のように2桁ずつ空白区切り。省略は '…'
  text?: string;       // HTTP行やSDP行などテキストのフィールド
  lineBreak?: boolean; // text の後で改行して表示
  desc?: string;
  bits?: BitField[];   // フラグなど1バイト内の分解(クリックで展開)
}

export interface Packet {
  name: string;                 // 'WebSocketフレーム'
  layers?: string[];            // カプセル化の外側から ['IPv4', 'UDP', 'STUN']
  fields: Field[];
  note?: string;
  fictional?: boolean;          // 架空フォーマットなら true(画面に明示)
  view?: 'decrypted';           // 実際は暗号化されている部分を復号後の姿で見せる場合
}

export interface Step {
  id: string;          // URLのハッシュに使う(例: 'upgrade')
  title: string;
  hops: Hop[];
  body: string;        // 2〜4文の短いMarkdown。<p>単位
  packet?: Packet;     // なければ「パケットなし」と表示
}

export interface Lesson {
  id: string;          // 'websocket'
  part: 1 | 2 | 3 | 4 | 5 | 6;
  order: number;
  title: string;
  tagline: string;     // 一覧に出す1行
  lead: string;        // レッスン冒頭の2〜3文
  lanes: Lane[];
  steps: Step[];
  sources: { label: string; url: string }[];  // RFCなど一次資料
  lastVerified: string;  // 'YYYY-MM-DD'。内容を一次資料と突き合わせた日
}
```

構造チェックのテスト(`lessons.schema.test.ts`)で次を全レッスンに対して確かめる。

- Hop の from/to がすべて実在する Lane.id を指している
- Field は hex と text のどちらか一方だけを持つ
- hex は `^([0-9A-F]{2}|…)( ([0-9A-F]{2}|…))*$` に一致する(大文字)
- bits の幅の合計が、そのフィールドのバイト数×8と一致する
- Step.id がレッスン内で一意で、sources が1件以上ある

### コンポーネント仕様

- **SequenceDiagram**:レーンは等間隔の縦線。手順ごとにグループ化し、現在は濃く、過去は45%、未来は10%の透明度で描く。現在の手順に入ると、パケットの点が矢印に沿って順に移動し、届いた矢印から濃くなる。`lost` は中間で×印。図の手順をクリックするとその手順へ移る。
- **StepPanel**:手順番号、見出し、本文、前へ・自動再生・次へ、手順ドット。←→キーで移動、Spaceで自動再生の切り替え。自動再生は約5秒ごと。
- **PacketInspector**:上段にカプセル化の帯(`layers`)、中段にバイト列、下段にフィールド表。フィールドは6色を順に割り当て、バイトと表の行はホバーでもキーボードのフォーカスでも互いに強調する。`bits` を持つ行は開くとビット単位の図が出る。`fictional` と `view: 'decrypted'` は表の上に注記として必ず出す。
- **速度切り替え**:アニメーション速度を 0.5× / 1× / 2× で選べる。設定は localStorage に保存。
- **前後のレッスン**:同じ部の中を順に進め、部の最後は比較ページへつなぐ。

## デザインシステム

プロトタイプの「方眼紙の上の設計図」という見た目を正式なトークンにする。参考サイトの暗い紺色の画面とは逆方向の、明るい紙色が基本で、ダークモードは同じ構造の色違いとする。目立たせるのはシーケンス図とパケットの動きだけにし、それ以外は静かに保つ。

| トークン | ライト  | ダーク  | 用途                          |
| -------- | ------- | ------- | ----------------------------- |
| --paper  | #E9EDE8 | #11151B | 背景                          |
| --panel  | #F7F8F4 | #191F27 | 図・パネルの面                |
| --ink    | #18202B | #E2E6E9 | 本文                          |
| --muted  | #5A6570 | #8E99A3 | 補足                          |
| --rule   | #C6CEC8 | #2D3641 | 罫線、レーン                  |
| --blue   | #2B57C9 | #7F9EFF | 接続制御の矢印                |
| --ochre  | #9A6A08 | #E2B04D | シグナリングの矢印            |
| --mag    | #B32C6E | #F07AAF | メディア・状態の矢印、消失の× |
| --teal   | #0F7F70 | #4FD0BB | データの矢印                  |

フィールドの6色(--f0〜--f5)は、薄い地色と濃い文字色の組でプロトタイプの値を使う。

- **文字**:本文と見出しは IBM Plex Sans JP(400 / 500 / 700)、バイト列と値だけ IBM Plex Mono。本文15px、行間1.75、1行は最大62字程度。
- **テーマ**:`prefers-color-scheme` に従い、`:root[data-theme]` で手動切り替えも可能にする。
- **動き**:パケットの移動だけ。ページを開いたときの演出やカードのホバー効果は付けない。`prefers-reduced-motion` のときは移動を省き、矢印をすぐ表示する。
- **アクセシビリティ**:色だけで意味を伝えない(凡例の文字、消失の×、フィールド名を必ず併記)。コントラストはWCAG AA。すべての操作をキーボードで行え、フォーカスは2pxの青い輪郭線で示す。手順が変わったら本文を `aria-live="polite"` で読み上げる。

## コンテンツ執筆ルールと正確性の検証

このサイトの価値はバイト列が正しいことにある。表示する16進は、テストで再計算できるか、「(例)」と明記するかのどちらかにする。

### 執筆ルール

- 本文は手順ごとに2〜4文。最初の文で「何が起きているか」を言い、次に「なぜそうするか」を言う。
- 説明はRFCなど一次資料を読んで自分の言葉で書く。他サイトや書籍の文章を写さない。
- 例のアドレスは文書用の予約範囲だけを使う。IPv4は 192.0.2.0/24・198.51.100.0/24・203.0.113.0/24、IPv6は 2001:db8::/32、ドメインは example.com / example.net。
- 乱数・チェックサム・暗号化部分など、再計算に意味のない値は desc に「(例)」と書くか、`…` で省略する。
- 架空フォーマット(ゲームのネットコード)は `fictional: true` にし、画面に必ず明示する。
- 日本語の引用は「」、プロトコル上の文字列(ヘッダー名、コマンド)は `code` で書く。

### バイト列の検証テスト

`src/lib/codecs/` に最小限のエンコーダーを書き、レッスンのhexと一致するかをVitestで確かめる。可能な限りRFC自身のテストベクターを使う。

| 対象             | 確かめること                                                   | 根拠                      |
| ---------------- | -------------------------------------------------------------- | ------------------------- |
| WebSocket        | マスクのXOR、長さの符号化、Sec-WebSocket-Accept のSHA-1+Base64 | RFC 6455 の例             |
| STUN             | XOR-MAPPED-ADDRESS のポートとアドレス、メッセージ長            | RFC 5769 のテストベクター |
| IPv4 / UDP / TCP | ヘッダーチェックサム、長さ、フラグのビット位置                 | RFC 791, 768, 9293        |
| DNS              | 名前のラベル符号化、ヘッダーのフラグ                           | RFC 1035                  |
| TLS 1.3          | レコードヘッダーとハンドシェイク型                             | RFC 8448 のトレース       |
| QUIC             | 可変長整数(varint)、Initialのヘッダー                          | RFC 9000, 9001 付録A      |
| DataChannel      | DCEPメッセージの並び                                           | RFC 8832                  |
| RTP              | V/P/X/CC、PT、タイムスタンプの進み方                           | RFC 3550                  |

プロトタイプのバイト列(WebSocket、STUN、DCEP、QUICのvarintなど)も移植時にこのテストを通す。通らない値は修正するか「(例)」にする。

## 開発フェーズとClaude Codeへの渡し方

土台→リアルタイム4章の移植→基礎17章の順に進める。各フェーズの終わりに `pnpm test` と `pnpm build` が通ることを区切りにする。

1. **土台**:Next.jsの雛形、`types.ts`、デザイントークン、3つの主要コンポーネント、レッスン画面。WebSocket 1本だけで画面を完成させる。
2. **リアルタイム移植**:プロトタイプの残り3章をデータに移し、`codecs/` とバイト列テストを書く。第6部の比較ページを作る。
3. **第2部と第3部**:UDP、TCP、DNS、TLS 1.3。ここでビット分解(`bits`)とカプセル化の帯を実装する。
4. **第1部と第4部**:Ethernet/ARP、IP、ICMP、DHCP、HTTP系4本。HTTPSの通しレッスンをトップに組み込む。
5. **第5部と仕上げ**:メールとリモートの5本、資料ページ、OGP画像(自作)、Playwrightとaxeのテスト。
6. **英語版**:UI辞書と本文の英訳を足す(任意)。

### 受け入れ基準

- [ ] 全21レッスンが構造チェックのテストを通る
- [ ] 一次資料のある全バイト列が codecs のテストで一致するか、「(例)」と明記されている
- [ ] すべての手順にキーボードだけで到達でき、axe-core で重大な違反がない
- [ ] 幅375pxのスマホで図・手順・分解が横にはみ出さない
- [ ] ライトとダークの両方で読める。reduced-motion で動きが止まる
- [ ] 参考サイト由来のコード・文章・画像が含まれていない

### 最初に渡す指示

リポジトリのルートに、この設計書を `docs/DESIGN.md`、プロトタイプを `prototype/realtime-protocols.html` として置き、Claude Codeに次のように頼む。

```text
docs/DESIGN.md を読み、要点とルールを CLAUDE.md にまとめてください。
そのあとフェーズ1(土台)だけを実装してください。

型・コンポーネント・レッスン画面を作り、pnpm test と pnpm build が通るところで止めてください。
既存の参考サイトのHTMLやコードは取得・参照しないでください。
```

フェーズごとに区切って頼むと、各段階で見た目とバイト列を確認しながら進められる。
